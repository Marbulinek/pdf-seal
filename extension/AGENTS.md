- **`extension/`** — Chromium MV3 extension ("PDF Seal Portal"), plain JS with no build step. It is not covered by tsc. vitest covers the `isAllowed()` match-pattern check in `shared.js` and guards the injection points (`test/extension/shared.test.ts`). Code reaches a page only on Allowed domains, gated on the tab's top-level URL. That covers four injection points: the `syncHook()` registered script (`matches`), `injectHook()` (`tabs.query({ url })`), the popup's `scan()`, which re-checks the tab URL right before injecting, and the background's `seal()`, which re-checks it too. The manifest must stay free of static `content_scripts` and of `host_permissions` beyond the PDF Seal origins. Its manual fixtures are `extension/test/embeds.html` (every embedding kind) and `extension/test/fake-nutrient.html`.
  - `page/export.js` exports `pdfsOnPage(exportId?)`, a self-contained function that runs in a frame's MAIN world in two modes.
    - With no argument, the popup runs it in all frames when the send button is clicked. Each candidate is checked in that call before it's returned: its first bytes must be `%PDF-`, via `check()` or else a full `get()`, with URLs reading only their first chunk. Failures are dropped. Cross-origin URLs and POST forms come back `unverified`. A single verified result is sent right away; anything else is shown as a pick list. It lists candidates without reading their bytes: Nutrient, pdf.js, the frame itself being a PDF, `embed`/`object`/`iframe`/link URLs (including `data:`, `blob:` and viewer `?file=` wrappers), bare base64 in the DOM, PDFs captured by the hook, and PDF-like `<form>`s, which are replayed on export. Nutrient instances count only in the frame (realm) that created them, because iframe viewers often also set `window.parent.instance`.
    - With an id, `background.js` runs it in that one frame to export the bytes.
    - A URL the page can't fetch (CORS) comes back as `{ fetch }`, and the background retries it. Before sending, the popup requests that origin's host permission while it still has the click's user gesture.
  - `page/hook.js` runs at `document_start` and is registered dynamically only for whitelisted domains. It captures Nutrient instances by wrapping `NutrientViewer.load`/`PSPDFKit.load`. It also captures PDFs that pass through `fetch`/`XMLHttpRequest` (raw, or base64 inside JSON/text) or `URL.createObjectURL`, or that are posted to a Web Worker (`Worker.prototype.postMessage`, copied before the transfer detaches them), into `window.__pdfSealCaptured`. The worker path covers viewers bundled through npm, such as Nutrient in an Angular app, which never put the SDK on `window`. Covered by `test/extension/hook.test.ts` and `test/fake-nutrient.html?bundled`.
  - The background then opens pdfSeal and posts `{ type: 'pdfseal:import', base64, name }` into that tab's main world.
  - `public/index.html` receives it with a `message` listener that accepts only same-window, same-origin messages, and passes it on to `analyzeBase64Pdf()` → `processNewFile()`. Keep that contract in sync on both sides.
  - The extension has its own release line (`extension-v*` tags, `extension/.releaserc.json`). It uses semantic-release-monorepo, so only commits touching `extension/` count. On merge to main, the `extension-release` job in `.github/workflows/release.yml` writes the version into `manifest.json`, zips the extension with `npm run build:extension`, and uploads and publishes it to the Chrome Web Store. Don't bump the manifest version by hand. Scope extension commits as `feat(extension):`/`fix(extension):` so the root app release ignores them.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What pdf-seal does

A browser-based PDF editor for preparing documents with signature form fields. Users upload a PDF, place and customize signature fields, and download or share the modified document. The app does **not** cryptographically sign PDFs — it inserts interactive form fields that downstream signing tools recognize.

Key features: upload/preview PDFs, place/move/resize/remove **unsigned signature fields** (every other field type and every signed signature is shown read-only for inspection), edit field properties (name, required), edit PDF metadata (title, author), browse a read-only document overview, download modified PDFs, share documents via WebSocket + WebRTC with encrypted transfer, browse and diff local version history, and reusable local signature templates.

## Repository layout

One npm package (a single `package.json`/`node_modules` at the root) holding three parts:

- **`app/`** — the Angular UI (the workspace config, `angular.json`, sits at the repo root next to `node_modules`; `app/tsconfig*.json` — app, specs and Web Workers — and `app/proxy.conf.json`), sources in `app/src`, static files (images, the tour's demo sample) in `app/public`. Builds to `dist/app/browser`. All client-side logic lives here, including the pure modules the specs cover most (e.g. `core/version-history.ts`); nothing is shared with the server.
- **`server/`** — the Express server: `server/server.ts`, its modules in `server/lib`, tests in `server/test` (helpers in `server/test/lib/helpers`), the sample/fixture generators in `server/scripts`, `server/tsconfig.json` and `server/esbuild.config.mjs`. Builds to `dist/server/server.js`.
- **`extension/`** — the Chromium extension (see `extension/AGENTS.md`), tests in `extension/test`.

At the root: `package.json` (all scripts), `angular.json`, `vitest.config.mjs` (the Node-side test projects), `playwright.config.ts` + `e2e/` (the end-to-end suite), `scripts/dev.mjs` (the `npm run dev` runner), `Dockerfile`, `railway.json` (Railway: build with the Dockerfile, health-check `/api/version`), `docs/`.

## Development commands

```bash
npm install             # Install dependencies (Node ^22.22.3 / ^24.15.0 / 26+, the Angular CLI's minimum; .nvmrc pins 24)
npm run build           # Build the whole solution: build:server, then build:web
npm run build:server    # Type-check the server (tsc -p server/tsconfig.json) and bundle it to dist/server/server.js (esbuild)
npm run build:web       # Build the Angular UI to dist/app/browser (ng build)
npm start               # Run the compiled server (node dist/server/server.js, serving dist/app/browser)
npm run dev             # Local dev on http://localhost:3000: `ng serve` (live reload/HMR) proxying /api and /signal to the API under `tsx watch` on port 3001 (scripts/dev.mjs, app/proxy.conf.json)
npm run dev:server      # Server only, under `tsx watch` on port 3000 (serves the last build of dist/app/browser, like production)
npm run build:demo-sample     # Regenerate the bundled Help-tour sample PDF + demo root CA
npm run build:perf-fixtures   # Regenerate app/public/perf-fixtures/ (gitignored) -- see docs/performance.md
npm run build:extension       # Zip extension/ into dist/pdf-seal-extension.zip (Chrome Web Store upload) -- see extension/AGENTS.md
```

There is no linter configured. There are two unit-test suites, both on Vitest, and `npm test` runs both (plus a Playwright e2e suite, below):

- **Node side** (`npm run test:server`, i.e. `vitest run` with the root `vitest.config.mjs`): two Vitest projects — `server` (`server/test`, mirroring `server/lib`, e.g. `server/test/lib/PdfSignatureTool.test.ts`) and `extension` (`extension/test`). Run one project with `npx vitest run --project server`, a single file with `npx vitest run server/test/lib/PdfSignatureTool.test.ts`, or filter by name with `npx vitest run -t "some test name"`.
- **Angular** (`npm run test:web`, i.e. `ng test --no-watch`): `app/src/**/*.spec.ts` next to the code they cover, run by `@angular/build:unit-test` in jsdom, with `app/src/test-setup.ts` stubbing the browser APIs jsdom lacks (`ResizeObserver`, canvas). Shared typed fixtures and the TestBed provider helper live in `app/src/app/testing/`. Narrow a run with `npx ng test --no-watch --include app/features/signatures` (paths are relative to `app/src/`) or `--filter "SignaturesStore"`.

The Angular specs never reach a server: `app/src/test-setup.ts` calls `blockNetwork()` (`app/src/app/testing/network.ts`), so a real `fetch`/`XMLHttpRequest`/`WebSocket` fails fast with "Unit tests never reach a server". A spec that exercises a server call mocks it — `mockFetch(handler)` + `jsonResponse()` from the same file (global stubs are undone after each test), or an `ApiService` fake in the TestBed providers.

**End-to-end** (`npm run test:e2e`, Playwright, `playwright.config.ts` at the root, specs in `e2e/`, type-checked by `e2e/tsconfig.json`): runs the built app in Chromium — the script runs `npm run build` and `playwright install chromium` (a no-op once downloaded) first, and `npx playwright test` alone re-runs against the existing build; Playwright starts `dist/server/server.js` itself on port 3100 (`E2E_PORT`), always a fresh process so the upload rate limiter starts empty. The specs drive the real UI through its stable DOM ids against the bundled demo sample. To use an already-installed Chromium instead, set `PLAYWRIGHT_CHROMIUM_PATH` and run `npx playwright test`. Keep the suite small: every document load costs a few `/api` uploads against the 60-per-15-minutes `uploadLimiter`.

Verify changes with `npm run build` (type checking + strict template checking), `npm test`, and manual testing against `http://localhost:3000`; add focused tests only for critical logic if needed.

Coverage (`server/lib/**` — `server/server.ts` has no HTTP-level tests) is measured with `npm run test:coverage` (vitest + `@vitest/coverage-v8`). Thresholds are enforced in `vitest.config.mjs`: statements/lines/functions at 90%, branches at 75% (many remaining branches are `??`/ternary fallbacks in formatting helpers not worth chasing individually). When adding logic to `server/lib/`, add or extend tests in the matching `server/test/lib/*.test.ts` file to keep coverage from regressing. The same script then runs `ng test --coverage` for the Angular code (`app/src/app/**`, reported only, no thresholds).

CI (`.github/workflows/ci.yml`) type-checks and bundles the server, builds the Angular UI, runs both test suites with coverage, runs the e2e suite (separate job, uploading the Playwright report on failure), and builds the Docker image (not pushed) on every PR into `main`. Releases (`.github/workflows/release.yml`) run semantic-release on pushes to `main`, deriving the version bump and CHANGELOG from Conventional Commits (`feat:`, `fix:`, etc.) — don't hand-edit `package.json`'s version or `CHANGELOG.md`.

## Architecture

- **`server/server.ts`** — Express app serving the built UI, handling multipart uploads (Multer), REST APIs for PDF operations, and WebSocket signaling for the share feature. The UI is the Angular build in `dist/app/browser` (`WEB_ROOT`, resolved from the working directory): hashed bundles are served with an immutable cache, `/vendor` with a 30-day one, and the SPA routes (`/`, `/signatures`, `/versions`, `/certificates`, `/share/:sessionId`) all answer with its `index.html` (no-cache; a 503 explains how to build it if it is missing). All routes and rate limiting live here; a catch-all registered after the last route returns JSON 404 for `/api/*` and, for everything else (and malformed share ids), the same `index.html` with a 404 status, where the Angular router renders its "Page not found" page — keep new routes above it. The mutating PDF routes (`/api/apply-changes`, etc.) share one shape: `upload.single("pdfDocument")` → sanitize the path → `PdfSignatureTool.open()` → mutate → `tool.save()` to a new `modified_<timestamp>.pdf` → respond → clean up temp files in `UPLOADS_DIR`. `/api/apply-changes?withFields=true` additionally returns the updated field list alongside the PDF, as a multipart response (`server/lib/MultipartResponse.ts`'s `encodeMultipart()`) — lets the client skip a redundant re-upload to `/api/info` just to learn what it already just told the server to create.
- **`server/lib/PdfSignatureTool.ts`** — Wraps pdf-lib to manage AcroForm signature fields and PDF metadata (open/edit/save a document). Also exports `truncateLongStrings(value, maxLength)`, a recursive cap on any string leaf in a plain JSON-shaped value (applied to `getDocumentInfoSummary()`'s `rawInfo`/`rawObjects`, and reused by `capSourceNode()` in `server/lib/PdfRevisionTool.ts`) — some Info-dictionary/object values are legitimately megabytes long, most notably this app's own embedded revision-chain JSON, which inlines every prior revision's bytes as base64. `/api/info`'s full summary no longer ships `rawObjects` at all (the Overview panel shows curated per-object details instead); it returns `annotations` from `listAnnotations()` — every non-widget, non-stamp page annotation (links, comments, markup) — alongside `fields`/`stamps`.
- **Editing scope** — PDF Seal edits unsigned signature fields only. One predicate, `isEditableField(f) = f.type === 'Signature' && !f.signed`, gates the client (`app/src/app/core/field-rules.ts`, used by the viewer overlays, the edit sheet, the remove button and the template batch replace), and `PdfSignatureTool._requireEditableField()` enforces the same rule server-side in `applyFieldOps()` (`add` with `type:'text'`, and `edit`/`remove` of non-signature or signed fields, throw). `toBytes()` saves with `updateFieldAppearances: false` so unrelated fields are never regenerated. Legacy `'text'` template items are kept/exported but skipped on placement (`'unsupported-type'`). Overview-sheet jumps to Certificates/Signatures record `diagnosticOrigin` and show a "Back to document" button.
- **`server/lib/PdfRevisionTool.ts`** — Compares PDF revisions at the raw-object level to detect changes (added/removed/modified signature fields, metadata changes); powers the Versions panel's compare view. `diffRawObjects()`/`describeRawObject()` contain the core diffing logic — rectangle (Rect) entries for annotations must be consolidated rather than reported as duplicate changes.
- **Local version history** lives entirely client-side, in the browser's IndexedDB (`pdfseal-versions`) — the server only ever handles the current document unless a request explicitly asks to diff/embed snapshots (`/api/revisions`, `/api/revisions/diff`; there is no server route for reading back stored history, unlike the removed `/api/revisions/embedded`). The store has three object stores, each keyed by `[sessionId, index]` (or `sessionId` alone for `versionSessions`):
  - `versionMeta` — one row per stored version: `source`/`saveKind` (as classified by `app/src/app/core/version-history.ts`), a `versionKey` (a fresh id minted per version, not the reused-after-undo `index`, used to disambiguate a row whose index was overwritten by a different edit), `storage: 'full' | 'delta'` plus a `baseKey` when it's a delta, and a persisted `summary` (badges/diff-ability info computed once and cached, instead of re-derived from bytes on every Versions panel open).
  - `versionBytes` — the actual PDF bytes for a version. An incremental save (its bytes are the previous version's bytes with something appended — see `classifySave()`) is stored as a `delta` (just the appended tail) rather than a second full copy; reading it back walks the `baseKey` chain (`versionReadPlan()`) and reconstructs via `Blob` concatenation.
  - `versionSessions` — lightweight per-session bookkeeping (used by the idle sweep that clears stale sessions without reading every version's bytes).

  The store is wrapped by `VersionStoreService` (`app/src/app/core/version-store.service.ts`). A freshly uploaded/imported/edited PDF is hydrated into this store client-side (`hydrateRevisions()`/`hydrateNativeChain()`/`hydrateBundledChain()`), streaming one version at a time rather than holding the whole chain in memory: it recognizes both this app's own embedded `PdfSealRevisionChainV1` format and a genuine native incremental-update chain (`startxref ... %%EOF` boundaries). There is no `/api/revisions/embedded` server round trip for this anymore — it was removed in favor of the client doing this work itself.

  Field-edit undo/redo (`DocumentService.captureSnapshot()`/`applySnapshot()`, with the stacks in `SignaturesStore`) is intentionally lightweight: an undo entry is the `File` object plus cloned field arrays and a few identifiers (`documentSessionId`, `documentRevisionCount`, `activeVersionKey`) — never a duplicated pdf.js document or a copy of the PDF's bytes. `activeVersionKey` (not just `documentRevisionCount`) uniquely identifies the exact stored version a snapshot points at, immune to an index being reused for different bytes after an undo/redo sequence. Restoring a snapshot only re-opens a pdf.js document when it targets a different file than the one currently open.
- **`app/src/app/features/signatures/signature-templates.ts`** — pure logic for the Signatures panel's local signature templates (store normalization, capturing a placed field as a template item (`templateItemFromField`/`upsertTemplateItem`), field-name de-duplication, batch placement planning, moving an item between lists, and the JSON export/import format used by the backup buttons in Settings). Template items are never typed in by hand — they're captured from fields already placed on the document, so there is no numeric size/position editing anywhere in the UI. `TemplatesStore` drives the UI with it.
- **`app/src/app/core/version-history.ts`** — pure logic behind the Versions panel's timeline: classifying how each locally-stored save was produced (`classifySave` → `'initial' | 'identical' | 'incremental' | 'rewrite'`, based on whether the new bytes are the previous save's bytes with something appended), building the ordered badge list for one entry (`versionBadges` — Original/Imported, Incremental update/Full rewrite, Current, Signed, and an "earlier signatures may not verify" warning when a rewrite follows a signed entry), the "show only incremental updates" filter (`filterVersions`), and the labelled group breaks drawn between runs of like saves in the timeline (`versionGroupDividers` — one divider per change of save kind; `initial` groups with `rewrite`, while `identical` and legacy saveKind-less entries stay inside whatever run they sit in), and the collapsible stacks drawn for runs of consecutive versions sharing a displayed modification time (`versionStacks` — never crossing a group divider; purely visual, each version keeps its own card inside). A **version** here is any full save this browser has stored for the document (a fresh upload, an imported/embedded revision chain, or an edit) — most are full rewrites of the PDF, not PDF incremental updates; only saves that literally append to the previous file's bytes are badged "Incremental update". `VersionStoreService`, `DocumentService` and the `VersionsStore` use it. Its `findRevisionEndOffsets()` is a byte-level twin of the server's `PdfRevisionTool.findRevisionBoundaries()` regex scan; both specs pin the same offsets, so keep them in step.
- **Diagnostic links** — `version-history.ts`'s `elementVersionHistory(versions, {kind,key})` finds the first stored version (and signed version) containing a field/signature/stamp by name using the cached per-version summaries; it drives the Overview sheet's "Find in version history" → Versions diff (pre-filtered via the `VersionsStore`'s `pendingFilterTerm`). Each `ReportSignature` in `server/lib/PdfCertificateReport.ts` carries `revisionCoverage: {coveredRevision, revisionCount}` (ByteRange end vs. `PdfRevisionTool.findRevisionBoundaries()`), and `sig.docMdp` becomes `unknown` when the file grew after signing (later changes are never checked against P). The "Show changes after signing" link only appears when the local versions are this file's native chain.
- **`app/src/app/features/overview/document-overview.ts`** — pure logic behind the Overview panel (the `metadata` section; nav label "Overview"): `curateRawEntries()` turns a raw dictionary record into readable "Technical details" rows (friendly labels, decoded `/F`/`/Ff` flags, rounded `/Rect`, summarized `/ByteRange`/binary/long values), `overviewItems()` flattens fields/stamps/annotations into the one list (signature | stamp | field | link | comment, sorted by page then top-to-bottom) that drives both the list and the PDF hotspots, and `atAGlanceChips()` picks the at-a-glance chips. `OverviewStore` drives the UI with it. While Overview is open, the viewer outlines stamps/links/comments on the page (`OverviewStore.hotspots`; fields and signatures reuse `.field-overlay`), clicking one opens `#overviewSheet`, and the eye toggles hide a kind via `body[data-overview-hide]`.
- **`app/src/app/features/tour/demo-tour.ts`** — pure logic behind the in-app Help tour: popover/spotlight geometry (`computePopoverPosition`, `spotlightRect`) and step navigation (`findStepIndex`, `chapterStartIndex`); the tour's settings override is merged by `mergeSettingsOverride()` in `core/settings.service.ts`. The tour itself (`app/src/app/features/tour/`: `TourService`, the 31-step/8-chapter script in `tour-steps.ts`, and the settings/template sandboxing; `app/src/app/shell/tour-overlay/` draws it) uses it. The bundled sample document the tour runs against (`app/public/assets/demo/pdf-seal-sample.pdf`, plus `pdf-seal-demo-root-ca.pem` for the Certificates chapter's trust-simulation demo) is generated by `server/scripts/build-demo-sample.ts` (`npm run build:demo-sample`), which reuses `server/test/lib/helpers/certificateFactory.ts` and `server/test/lib/helpers/pdfSigner.ts` to mint a real certificate chain and produce a genuinely three-revision, signed PDF. `server/test/demoSample.test.ts` guards the committed sample against silent rot when field/metadata/revision-chain handling in `server/lib/PdfSignatureTool.ts` changes — regenerate the sample and re-run tests if it fails.
- **The Angular UI (`app/`)** — Angular 22: standalone components only, signals for all reactivity, zoneless change detection, `OnPush` everywhere, strict templates, no `any`. Layout and behaviour match the previous single-page UI one-to-one, down to the DOM ids and classes the global stylesheet (`app/src/styles.css`) and the tour's selectors rely on — keep them stable.
  - `app/src/app/app.ts` is the shell: notifications, tour overlay, pending-changes bar, top bar, the viewer (left), the routed section column (right) with its sliding sheets, the footer, and every modal. For an unknown URL it renders only the full-page `NotFoundPage` (`features/not-found/`, the catch-all route) instead of the workspace. It reacts to section changes (deselect on leaving Signatures, suspend/resume the Versions diff, close sheets, lazy-load each section's data) and owns the global keys (Escape closes the innermost modal first, then a sheet; Ctrl/Cmd+Z undo/redo in Signatures).
  - `app/src/app/app.routes.ts`: one lazily-loaded route per section (`''` Overview — the default, `signatures`, `versions`, `certificates`, and `share/:sessionId`, which opens Overview and starts the receive flow; a `canMatch` sends malformed session ids to the 404 page), plus the `**` "Page not found" route. Modals (`shell/modals/`) and sheets (`shell/sheets/`) load in `@defer (on idle)` blocks. Structural components use attribute selectors (`section[appViewer]`, `aside[appEditSheet]`, `div[appSettingsModal]`…) so the rendered DOM is the original one; wrapper hosts use `display: contents`.
  - State: the four feature states are NgRx SignalStores — `OverviewStore`, `SignaturesStore` (+ `TemplatesStore`), `VersionsStore`, `CertificatesStore` (each `features/<name>/<name>.store.ts`, `providedIn: 'root'`, immutable state, `patchState` only). The open document lives in `DocumentStore` (`core/document.store.ts`); fields carry a client-side `uid` so selection never depends on object identity. Imperative work (pdf.js rendering, IndexedDB, WebRTC) lives in services: `DocumentService` (`processNewFile`, apply, snapshots), `ViewerService` (canvas, zoom, diff view mode), `VisualDiffService`, `VersionStoreService`, `ShareService`, `ExportService`, `TourService`, `PdfJsService`. Cross-feature calls go through the ports in `core/ports.ts` (bound in `core/port-providers.ts`, resolved lazily) to avoid DI/import cycles.
  - Pure view-model functions sit next to each store (`overview-model.ts`, `versions-model.ts`, `certificates-model.ts`, `signatures/field-ops.ts`) and are what the specs exercise most. Shared presentational components (hero/facts/flags, cert chain, validation list, validity timeline, meta tree, diff bits) live in `app/src/app/shared/`.
  - pdf.js is the `pdfjs-dist` npm package (legacy build — the modern one needs built-ins like `Map.prototype.getOrInsertComputed` that browsers don't ship yet), never a CDN: `PdfJsService` imports it lazily (its own chunk, warmed up at idle), the `angular.json` assets copy its worker to `/vendor/pdfjs/`, and its types are aliased in `core/pdfjs-types.ts` (`destroyDocument()`, `toViewportRectangle()` cover APIs pdf.js 5+ removed). Everything in `app/public/` is copied verbatim into the build output. The visual diff's pixel comparison runs in a Web Worker bundled by the Angular build (`features/versions/diff.worker.ts`, started with `new Worker(new URL('./diff.worker', import.meta.url))`, type-checked by `app/tsconfig.worker.json`); its messages are typed in `diff-worker-protocol.ts`, and it imports the stroke grouping from `visual-diff-strokes.ts`. Development builds expose the services/stores on `window.pdfSeal` for the console-driven scenarios in `docs/performance.md`; every build exposes `window.processNewFile`, which the browser extension probes for (see `extension/AGENTS.md`).
  - Every section's right panel opens with the Overview's visual vocabulary — an `<app-ov-hero>` plus `<app-ov-facts>` tiles (`#sigSectionHero`, `#revisionsHero`, the Certificates summary), and rows/collapsibles styled like `.overview-row`/`.overview-more`.
- **Sharing** — `/share/:sessionId` pages plus a `WebSocketServer` in `server/server.ts` handle signaling only (the browser side is `ShareService`, `app/src/app/features/share/share.service.ts`); the actual PDF bytes move browser-to-browser over a WebRTC data channel in chunks with backpressure, verified by the recipient via SHA-256. Share sessions exist only in server memory (`socketSessions`/session maps in `server/server.ts`) and expire after 15 minutes — there is no persistence to design around.

## Key rules

- **Filesystem safety**: any request-derived path must be reduced to a bare filename with `path.basename()` and rejoined onto the fixed, trusted `UPLOADS_DIR` (`server/server.ts`) before touching `fs.*`. Inline this check next to the fs call itself — see the pattern around line 39 of `server/server.ts`.
- **Rate limiting**: every new HTTP route needs `generalLimiter`, plus `uploadLimiter` if it handles file uploads.
- **No CDN scripts**: install third-party libraries from npm and bundle them through the Angular build (or, for files that must stay separate like workers, copy them to `/vendor` via `angular.json` assets) instead of loading from external CDNs.
- **Angular conventions**: follow the Angular agent skill in `.claude/skills/angular-developer` (installed from `angular/skills`). In this codebase that means: standalone components, signals (`signal`/`computed`/`linkedSignal`/`resource`/`input`/`output`/`viewChild`) rather than RxJS for state, NgRx SignalStore for feature state, `ChangeDetectionStrategy.OnPush`, no `any` (narrow `unknown` instead), and keep the existing DOM ids/classes stable.
  - Derive state with `computed`/`linkedSignal` (`withLinkedState` in a store) — never by `.set()`/`patchState` inside an `effect`. Effects only sync signals to the DOM or other imperative APIs (`untracked` around the imperative part).
  - Query your own template with `viewChild`/`viewChildren`, not `document.querySelector`/`getElementById`.
  - One component per file, named after its class in kebab-case (`TemplateNameModal` → `template-name-modal.ts`); a template over ~60 lines lives in a sibling `.html` (`templateUrl`).
- **Proxy trust**: `app.set("trust proxy", 1)` is intentional for Railway's single proxy hop — don't change it without understanding the tradeoff.

## Working guidelines

- **PDF field operations**: start at `server/lib/PdfSignatureTool.ts`.
- **Version tracking**: changes to field detection or diff logic go in `server/lib/PdfRevisionTool.ts`; changes to how a save is classified or badged (Original/Imported, Incremental update/Full rewrite, Current, Signed) go in `app/src/app/core/version-history.ts`. A "version" is any full save stored locally (upload, imported chain entry, or edit) — only a save whose bytes are an exact byte-for-byte extension of the previous one counts as an "Incremental update"; everything else is a "Full rewrite", even if the PDF itself used a true incremental-update structure internally. Verify the Versions panel displays badges and changes correctly after edits.
- **File uploads**: keep cleanup correct in `server/server.ts`; follow the filesystem-safety rule above.
- **New routes**: add rate limiting and follow the security conventions above. A new client-side section also needs its path in the server's SPA route list.
- **UI changes**: update the component (template + class) and `app/src/styles.css` together; put new logic in the feature's store or a pure `*-model.ts` function with a spec beside it.
- **Sharing**: keep WebSocket signaling logic in `server/server.ts` and the browser-side WebRTC flow (`ShareService`) in sync. Share sessions exist only in server memory and expire after 15 minutes.

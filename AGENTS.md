# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What pdf-seal does

A browser-based PDF editor for preparing documents with signature form fields. Users upload a PDF, place and customize signature fields, and download or share the modified document. The app does **not** cryptographically sign PDFs — it inserts interactive form fields that downstream signing tools recognize.

Key features: upload/preview PDFs, place/move/resize/remove **unsigned signature fields** (every other field type and every signed signature is shown read-only for inspection), edit field properties (name, required), edit PDF metadata (title, author), browse a read-only document overview, download modified PDFs, share documents via WebSocket + WebRTC with encrypted transfer, browse and diff local version history, and reusable local signature templates.

## Development commands

```bash
npm install             # Install dependencies (Node ^22.22.3 / ^24.15.0 / 26+, the Angular CLI's minimum)
npm run dev             # Angular build --watch + API under `tsx watch`, served together on http://localhost:3000
npm run dev:api         # API only (tsx server.ts)
npm run dev:web         # Angular dev server with HMR on http://localhost:4200 (proxies /api and /signal, see proxy.conf.json)
npm run build           # Type-check the API (tsc), bundle it to dist/server.js (esbuild), build the UI to dist/web/browser (ng build)
npm start               # Run the compiled server (node dist/server.js, serving dist/web/browser)
npm run build:demo-sample     # Regenerate the bundled Help-tour sample PDF + demo root CA
npm run build:perf-fixtures   # Regenerate public/perf-fixtures/ (gitignored) -- see docs/performance.md
npm run build:extension       # Zip extension/ into dist/pdf-seal-extension.zip (Chrome Web Store upload) -- see extension/AGENTS.md
```

There is no linter configured. There are two unit-test suites, both on Vitest, and `npm test` runs both:

- **Backend** (`npm run test:lib`): `test/`, mirroring the `lib/` layout (e.g. `test/lib/PdfSignatureTool.test.ts`). Run a single file with `npx vitest run test/lib/PdfSignatureTool.test.ts` or filter by name with `npx vitest run -t "some test name"`.
- **Angular** (`npm run test:web`, i.e. `ng test --no-watch`): `src/**/*.spec.ts` next to the code they cover, run by `@angular/build:unit-test` in jsdom. Shared typed fixtures and the TestBed provider helper live in `src/app/testing/`. Narrow a run with `npx ng test --no-watch --include app/features/signatures` (paths are relative to `src/`) or `--filter "SignaturesStore"`.

Verify changes with `npm run build` (type checking + strict template checking), `npm test`, and manual testing against `http://localhost:3000`; add focused tests only for critical logic if needed.

Coverage (`lib/**` only — `server.ts` has no HTTP-level tests) is measured with `npm run test:coverage` (vitest + `@vitest/coverage-v8`). Thresholds are enforced in `vitest.config.mjs`: statements/lines/functions at 90%, branches at 75% (many remaining branches are `??`/ternary fallbacks in formatting helpers not worth chasing individually). When adding logic to `lib/`, add or extend tests in the matching `test/lib/*.test.ts` file to keep coverage from regressing. The same script then runs `ng test --coverage` for the Angular code (`src/app/**`, reported only, no thresholds).

CI (`.github/workflows/ci.yml`) type-checks and bundles the API, builds the Angular UI, runs both test suites with coverage, and builds the Docker image (not pushed) on every PR into `main`. Releases (`.github/workflows/release.yml`) run semantic-release on pushes to `main`, deriving the version bump and CHANGELOG from Conventional Commits (`feat:`, `fix:`, etc.) — don't hand-edit `package.json`'s version or `CHANGELOG.md`.

## Architecture

- **`server.ts`** — Express app serving the built UI, handling multipart uploads (Multer), REST APIs for PDF operations, and WebSocket signaling for the share feature. The UI is the Angular build in `dist/web/browser` (`WEB_ROOT`): hashed bundles are served with an immutable cache, `/vendor` with a 30-day one, and the SPA routes (`/`, `/signatures`, `/versions`, `/certificates`, `/share/:sessionId`) all answer with its `index.html` (no-cache; a 503 explains how to build it if it is missing). All routes and rate limiting live here; a catch-all registered after the last route returns JSON 404 for `/api/*` and the built `404.html` otherwise — keep new routes above it. The mutating PDF routes (`/api/apply-changes`, etc.) share one shape: `upload.single("pdfDocument")` → sanitize the path → `PdfSignatureTool.open()` → mutate → `tool.save()` to a new `modified_<timestamp>.pdf` → respond → clean up temp files in `UPLOADS_DIR`. `/api/apply-changes?withFields=true` additionally returns the updated field list alongside the PDF, as a multipart response (`lib/MultipartResponse.ts`'s `encodeMultipart()`) — lets the client skip a redundant re-upload to `/api/info` just to learn what it already just told the server to create.
- **`lib/PdfSignatureTool.ts`** — Wraps pdf-lib to manage AcroForm signature fields and PDF metadata (open/edit/save a document). Also exports `truncateLongStrings(value, maxLength)`, a recursive cap on any string leaf in a plain JSON-shaped value (applied to `getDocumentInfoSummary()`'s `rawInfo`/`rawObjects`, and reused by `capSourceNode()` in `lib/PdfRevisionTool.ts`) — some Info-dictionary/object values are legitimately megabytes long, most notably this app's own embedded revision-chain JSON, which inlines every prior revision's bytes as base64. `/api/info`'s full summary no longer ships `rawObjects` at all (the Overview panel shows curated per-object details instead); it returns `annotations` from `listAnnotations()` — every non-widget, non-stamp page annotation (links, comments, markup) — alongside `fields`/`stamps`.
- **Editing scope** — PDF Seal edits unsigned signature fields only. One predicate, `isEditableField(f) = f.type === 'Signature' && !f.signed`, gates the client (`src/app/core/field-rules.ts`, used by the viewer overlays, the edit sheet, the remove button and the template batch replace), and `PdfSignatureTool._requireEditableField()` enforces the same rule server-side in `applyFieldOps()` (`add` with `type:'text'`, and `edit`/`remove` of non-signature or signed fields, throw). `toBytes()` saves with `updateFieldAppearances: false` so unrelated fields are never regenerated. Legacy `'text'` template items are kept/exported but skipped on placement (`'unsupported-type'`). Overview-sheet jumps to Certificates/Signatures record `diagnosticOrigin` and show a "Back to document" button.
- **`lib/PdfRevisionTool.ts`** — Compares PDF revisions at the raw-object level to detect changes (added/removed/modified signature fields, metadata changes); powers the Versions panel's compare view. `diffRawObjects()`/`describeRawObject()` contain the core diffing logic — rectangle (Rect) entries for annotations must be consolidated rather than reported as duplicate changes.
- **Local version history** lives entirely client-side, in the browser's IndexedDB (`pdfseal-versions`) — the server only ever handles the current document unless a request explicitly asks to diff/embed snapshots (`/api/revisions`, `/api/revisions/diff`; there is no server route for reading back stored history, unlike the removed `/api/revisions/embedded`). The store has three object stores, each keyed by `[sessionId, index]` (or `sessionId` alone for `versionSessions`):
  - `versionMeta` — one row per stored version: `source`/`saveKind` (as classified by `lib/VersionHistory.ts`), a `versionKey` (a fresh id minted per version, not the reused-after-undo `index`, used to disambiguate a row whose index was overwritten by a different edit), `storage: 'full' | 'delta'` plus a `baseKey` when it's a delta, and a persisted `summary` (badges/diff-ability info computed once and cached, instead of re-derived from bytes on every Versions panel open).
  - `versionBytes` — the actual PDF bytes for a version. An incremental save (its bytes are the previous version's bytes with something appended — see `classifySave()`) is stored as a `delta` (just the appended tail) rather than a second full copy; reading it back walks the `baseKey` chain (`versionReadPlan()`) and reconstructs via `Blob` concatenation.
  - `versionSessions` — lightweight per-session bookkeeping (used by the idle sweep that clears stale sessions without reading every version's bytes).

  The store is wrapped by `VersionStoreService` (`src/app/core/version-store.service.ts`). A freshly uploaded/imported/edited PDF is hydrated into this store client-side (`hydrateRevisions()`/`hydrateNativeChain()`/`hydrateBundledChain()`), streaming one version at a time rather than holding the whole chain in memory: it recognizes both this app's own embedded `PdfSealRevisionChainV1` format and a genuine native incremental-update chain (`startxref ... %%EOF` boundaries). There is no `/api/revisions/embedded` server round trip for this anymore — it was removed in favor of the client doing this work itself.

  Field-edit undo/redo (`DocumentService.captureSnapshot()`/`applySnapshot()`, with the stacks in `SignaturesStore`) is intentionally lightweight: an undo entry is the `File` object plus cloned field arrays and a few identifiers (`documentSessionId`, `documentRevisionCount`, `activeVersionKey`) — never a duplicated pdf.js document or a copy of the PDF's bytes. `activeVersionKey` (not just `documentRevisionCount`) uniquely identifies the exact stored version a snapshot points at, immune to an index being reused for different bytes after an undo/redo sequence. Restoring a snapshot only re-opens a pdf.js document when it targets a different file than the one currently open.
- **`lib/SignatureTemplates.ts`** — pure logic for the Signatures panel's local signature templates (store normalization, capturing a placed field as a template item (`templateItemFromField`/`upsertTemplateItem`), field-name de-duplication, batch placement planning, moving an item between lists, and the JSON export/import format used by the backup buttons in Settings). Template items are never typed in by hand — they're captured from fields already placed on the document, so there is no numeric size/position editing anywhere in the UI. The Angular `TemplatesStore` imports it directly, so there is one copy of the logic.
- **`lib/VersionHistory.ts`** — pure logic behind the Versions panel's timeline: classifying how each locally-stored save was produced (`classifySave` → `'initial' | 'identical' | 'incremental' | 'rewrite'`, based on whether the new bytes are the previous save's bytes with something appended), building the ordered badge list for one entry (`versionBadges` — Original/Imported, Incremental update/Full rewrite, Current, Signed, and an "earlier signatures may not verify" warning when a rewrite follows a signed entry), the "show only incremental updates" filter (`filterVersions`), and the labelled group breaks drawn between runs of like saves in the timeline (`versionGroupDividers` — one divider per change of save kind; `initial` groups with `rewrite`, while `identical` and legacy saveKind-less entries stay inside whatever run they sit in), and the collapsible stacks drawn for runs of consecutive versions sharing a displayed modification time (`versionStacks` — never crossing a group divider; purely visual, each version keeps its own card inside). A **version** here is any full save this browser has stored for the document (a fresh upload, an imported/embedded revision chain, or an edit) — most are full rewrites of the PDF, not PDF incremental updates; only saves that literally append to the previous file's bytes are badged "Incremental update". The Angular `VersionsStore` imports it directly, so there is one copy of the logic.
- **Diagnostic links** — `lib/VersionHistory.ts`'s `elementVersionHistory(versions, {kind,key})` finds the first stored version (and signed version) containing a field/signature/stamp by name using the cached per-version summaries; it drives the Overview sheet's "Find in version history" → Versions diff (pre-filtered via the `VersionsStore`'s `pendingFilterTerm`). Each `ReportSignature` in `lib/PdfCertificateReport.ts` carries `revisionCoverage: {coveredRevision, revisionCount}` (ByteRange end vs. `findRevisionEndOffsets`), and `sig.docMdp` becomes `unknown` when the file grew after signing (later changes are never checked against P). The "Show changes after signing" link only appears when the local versions are this file's native chain.
- **`lib/DocumentOverview.ts`** — pure logic behind the Overview panel (the `metadata` section; nav label "Overview"): `curateRawEntries()` turns a raw dictionary record into readable "Technical details" rows (friendly labels, decoded `/F`/`/Ff` flags, rounded `/Rect`, summarized `/ByteRange`/binary/long values), `overviewItems()` flattens fields/stamps/annotations into the one list (signature | stamp | field | link | comment, sorted by page then top-to-bottom) that drives both the list and the PDF hotspots, and `atAGlanceChips()` picks the at-a-glance chips. The Angular `OverviewStore` imports it directly. While Overview is open, the viewer outlines stamps/links/comments on the page (`OverviewStore.hotspots`; fields and signatures reuse `.field-overlay`), clicking one opens `#overviewSheet`, and the eye toggles hide a kind via `body[data-overview-hide]`.
- **`lib/DemoTour.ts`** — pure logic behind the in-app Help tour: popover/spotlight geometry (`computePopoverPosition`, `spotlightRect`), step navigation (`findStepIndex`, `chapterStartIndex`), and settings-override merging (`mergeSettingsOverride`). The Angular tour (`src/app/features/tour/`: `TourService`, the 31-step/8-chapter script in `tour-steps.ts`, and the settings/template sandboxing; `src/app/shell/tour-overlay/` draws it) imports it directly. The bundled sample document the tour runs against (`public/assets/demo/pdf-seal-sample.pdf`, plus `pdf-seal-demo-root-ca.pem` for the Certificates chapter's trust-simulation demo) is generated by `scripts/build-demo-sample.ts` (`npm run build:demo-sample`), which reuses `test/lib/helpers/certificateFactory.ts` and `test/lib/helpers/pdfSigner.ts` to mint a real certificate chain and produce a genuinely three-revision, signed PDF. `test/demoSample.test.ts` guards the committed sample against silent rot when field/metadata/revision-chain handling in `lib/PdfSignatureTool.ts` changes — regenerate the sample and re-run tests if it fails.
- **The Angular UI (`src/`, `angular.json`)** — Angular 22: standalone components only, signals for all reactivity, zoneless change detection, `OnPush` everywhere, strict templates, no `any`. Layout and behaviour match the previous single-page UI one-to-one, down to the DOM ids and classes the global stylesheet (`src/styles.css`) and the tour's selectors rely on — keep them stable.
  - `src/app/app.ts` is the shell: notifications, tour overlay, pending-changes bar, top bar, the viewer (left), the routed section column (right) with its sliding sheets, the footer, and every modal. It reacts to section changes (deselect on leaving Signatures, suspend/resume the Versions diff, close sheets, lazy-load each section's data) and owns the global keys (Escape closes the innermost modal first, then a sheet; Ctrl/Cmd+Z undo/redo in Signatures).
  - `src/app/app.routes.ts`: one lazily-loaded route per section (`''` Overview — the default, `signatures`, `versions`, `certificates`, and `share/:sessionId`, which opens Overview and starts the receive flow). Modals (`shell/modals/`) and sheets (`shell/sheets/`) load in `@defer (on idle)` blocks. Structural components use attribute selectors (`section[appViewer]`, `aside[appEditSheet]`, `div[appSettingsModal]`…) so the rendered DOM is the original one; wrapper hosts use `display: contents`.
  - State: the four feature states are NgRx SignalStores — `OverviewStore`, `SignaturesStore` (+ `TemplatesStore`), `VersionsStore`, `CertificatesStore` (each `features/<name>/<name>.store.ts`, `providedIn: 'root'`, immutable state, `patchState` only). The open document lives in `DocumentStore` (`core/document.store.ts`); fields carry a client-side `uid` so selection never depends on object identity. Imperative work (pdf.js rendering, IndexedDB, WebRTC) lives in services: `DocumentService` (`processNewFile`, apply, snapshots), `ViewerService` (canvas, zoom, diff view mode), `VisualDiffService`, `VersionStoreService`, `ShareService`, `ExportService`, `TourService`, `PdfJsService`. Cross-feature calls go through the ports in `core/ports.ts` (bound in `core/port-providers.ts`, resolved lazily) to avoid DI/import cycles.
  - Pure view-model functions sit next to each store (`overview-model.ts`, `versions-model.ts`, `certificates-model.ts`, `signatures/field-ops.ts`) and are what the specs exercise most. Shared presentational components (hero/facts/flags, cert chain, validation list, validity timeline, meta tree, diff bits) live in `src/app/shared/`.
  - pdf.js stays the self-hosted UMD build under `public/vendor/` (loaded on demand by `PdfJsService`, never from a CDN); everything in `public/` is copied verbatim into the build output. Development builds expose the services/stores on `window.pdfSeal` for the console-driven scenarios in `docs/performance.md`; every build exposes `window.processNewFile`, which the browser extension probes for (see `extension/AGENTS.md`).
  - Every section's right panel opens with the Overview's visual vocabulary — an `<app-ov-hero>` plus `<app-ov-facts>` tiles (`#sigSectionHero`, `#revisionsHero`, the Certificates summary), and rows/collapsibles styled like `.overview-row`/`.overview-more`.
- **Sharing** — `/share/:sessionId` pages plus a `WebSocketServer` in `server.ts` handle signaling only (the browser side is `ShareService`, `src/app/features/share/share.service.ts`); the actual PDF bytes move browser-to-browser over a WebRTC data channel in chunks with backpressure, verified by the recipient via SHA-256. Share sessions exist only in server memory (`socketSessions`/session maps in `server.ts`) and expire after 15 minutes — there is no persistence to design around.

## Key rules

- **Filesystem safety**: any request-derived path must be reduced to a bare filename with `path.basename()` and rejoined onto the fixed, trusted `UPLOADS_DIR` (`server.ts`) before touching `fs.*`. Inline this check next to the fs call itself — see the pattern around line 39 of `server.ts`.
- **Rate limiting**: every new HTTP route needs `generalLimiter`, plus `uploadLimiter` if it handles file uploads.
- **No CDN scripts**: self-host third-party libraries under `public/vendor/` (or bundle them through the Angular build) instead of loading from external CDNs.
- **Angular conventions**: standalone components, signals (`signal`/`computed`/`effect`/`input`/`output`/`viewChild`) rather than RxJS for state, NgRx SignalStore for feature state, `ChangeDetectionStrategy.OnPush`, no `any` (narrow `unknown` instead), and keep the existing DOM ids/classes stable.
- **Proxy trust**: `app.set("trust proxy", 1)` is intentional for Railway's single proxy hop — don't change it without understanding the tradeoff.

## Working guidelines

- **PDF field operations**: start at `lib/PdfSignatureTool.ts`.
- **Version tracking**: changes to field detection or diff logic go in `lib/PdfRevisionTool.ts`; changes to how a save is classified or badged (Original/Imported, Incremental update/Full rewrite, Current, Signed) go in `lib/VersionHistory.ts`. A "version" is any full save stored locally (upload, imported chain entry, or edit) — only a save whose bytes are an exact byte-for-byte extension of the previous one counts as an "Incremental update"; everything else is a "Full rewrite", even if the PDF itself used a true incremental-update structure internally. Verify the Versions panel displays badges and changes correctly after edits.
- **File uploads**: keep cleanup correct in `server.ts`; follow the filesystem-safety rule above.
- **New routes**: add rate limiting and follow the security conventions above.
- **UI changes**: update the component (template + class) and `src/styles.css` together; put new logic in the feature's store or a pure `*-model.ts` function with a spec beside it.
- **Sharing**: keep WebSocket signaling logic in `server.ts` and the browser-side WebRTC flow (`ShareService`) in sync. Share sessions exist only in server memory and expire after 15 minutes.
